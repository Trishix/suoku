# Configuration reference

Suoku has two credentials with different responsibilities:

| Setting | Used by | Purpose |
| --- | --- | --- |
| `SUOKU_API_TOKEN` | API and application clients | Authenticates access to the whole Suoku deployment |
| `SUOKU_PROVIDER_API_KEY` | Worker only | Authorizes the configured vision provider |

The model route is separate from the key:

```text
SUOKU_INSIGHT_MODEL=openai/YOUR_MODEL_ID
```

Supported route prefixes are `openai`, `anthropic`, `gemini`, `groq`, and `openrouter`.
OpenRouter routes usually contain an upstream provider, for example
`openrouter/anthropic/claude-3-5-sonnet`.

## Recommended initialization

Interactive setup hides keyboard input:

```bash
suoku init --provider openai --model YOUR_MODEL_ID
```

Automation can provide only the provider key through standard input:

```bash
secret-manager read provider-key | \
  suoku init --model openai/YOUR_MODEL_ID --provider-key-stdin
```

`init` generates a random service token and writes `.suoku/config.env` with directory mode
`0700` and file mode `0600`. It never prints the provider key or token. Existing config is
not overwritten unless `--force` is explicit.

## Environment precedence

The CLI reads `.suoku/config.env` literally; it does not evaluate shell substitutions. Process
environment variables override values in the file. This is useful in deployments:

```bash
SUOKU_API_TOKEN="$DEPLOYMENT_TOKEN" \
SUOKU_INSIGHT_MODEL="openrouter/provider/model" \
SUOKU_PROVIDER_API_KEY="$PROVIDER_KEY" \
suoku worker --data /data --model /models/siglip
```

The supported settings are:

| Variable | Default | Notes |
| --- | --- | --- |
| `SUOKU_API_TOKEN` | generated by `init` | Must be at least 32 characters for the API |
| `SUOKU_INSIGHT_MODEL` | none | Explicit provider/model route required for insights |
| `SUOKU_PROVIDER_API_KEY` | none | Never accepted through an HTTP request |
| `SUOKU_BASE_URL` | `http://127.0.0.1:8000` | CLI/client service URL |

## Separate API and worker configuration

The API needs only `SUOKU_API_TOKEN`. The worker needs the model, provider key, local model
directory, and the same data directory. In a container deployment, pass provider credentials
only to the insights-enabled worker override. See [releasing.md](releasing.md).

## Model preparation

`prepare-model` is the only normal command that downloads the local SigLIP model. It requires
an immutable 40-character model revision and writes a manifest containing file hashes:

```bash
suoku prepare-model .models/siglip --revision 7fd15f0689c79d79e38b1c2e2e2370a7bf2761ed
suoku doctor --model .models/siglip
```

Runtime loading is offline and verifies the manifest. Do not replace model files or manifests
in place; prepare a new directory and switch the worker after verification.

## Data directories

Use one data directory per deployment and share it between the API and worker. Native CLI
defaults to `.lake`; Compose uses the named `suoku-data` volume. A worker pointed at a
different directory will have its own queue, catalog, media, and model index.

Keep `.suoku`, `.lake`, `.models`, `.example-lake`, and `.example-output` out of version control.
